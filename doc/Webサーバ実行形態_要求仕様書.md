# ノードエディタアプリケーション Webサーバ実行形態 要求仕様書

**版数**: v0.1（ドラフト）
**作成日**: 2026-08-21
**対象プロジェクト**: Demo_Vue3_Sample2（ノードエディタ）

---

## 1. 目的

現行のElectronスタンドアロン実行形態に加え、Webサーバとして起動し、ブラウザから操作できる実行形態を追加する。これにより以下を実現する。

- サーバー端末上のブラウザから直接操作できる（従来のElectron版相当の使い方）
- LAN内の別端末からも、IPアドレスとポートを指定してブラウザ経由で操作できる
- 解析装置とのコマンド通信を伴うスクリプト実行は、装置と物理的に接続されたサーバー端末側で行う

---

## 2. 前提・スコープ

### 2.1 対象範囲

- 既存のECSコア（World, ComponentStore, HierarchyComponent等）およびVue UI層は、Electron版・Web版で共通利用する
- 差し替えが必要なのは、Node.jsのネイティブ機能を利用している以下の3箇所のみ
  1. 設定ファイルの読込・書込
  2. レシピファイルの読込・書込
  3. スクリプトファイルの実行（解析装置とのコマンド通信を含む）

### 2.2 スコープ外（本版では対応しない）

- 複数ユーザーによる同時編集・排他制御（本アプリは単一ユーザー操作を前提とする）
- インターネット経由でのリモートアクセス（LAN内利用を前提とする）
- ユーザー認証・アクセス権限管理の本格実装（必要性は3.5節で言及するが、詳細仕様は別途検討）

---

## 3. 機能要求

### 3.1 Webサーバ起動

- Node.js製のHTTPサーバー（Express等）を追加し、`0.0.0.0`でbindすることで、サーバー端末自身および同一LAN内の他端末からのアクセスを受け付ける
- サーバー起動時に、自端末のLAN上のIPアドレス一覧とポート番号を画面またはコンソールに表示し、他端末からの接続に必要な情報をユーザーが確認できるようにする
- サーバー起動と同時に、サーバー端末上で既定のブラウザを自動起動し、`http://localhost:<port>` を開く

### 3.2 UI配信

- Vue UIのビルド成果物（Vite出力）を静的ファイルとしてHTTPサーバーから配信する
- Electron版・Web版でVue UIコンポーネント資産を共通化し、ビルド成果物の差分を最小限にする

### 3.3 設定ファイル読込・書込のWeb対応

- 設定データの読込・書込をHTTP API（例: `GET /api/settings`, `PUT /api/settings`）として実装する
- サーバー端末のローカルディスク上に設定ファイルを保存する
- Electron版のIPC呼び出し（`ipcRenderer.invoke`）と、Web版のHTTP API呼び出しを、共通インターフェース（`FileService`等）を介して切り替え可能にする（Composition Rootでの実装差し替え）

### 3.4 レシピファイル読込・書込のWeb対応

- レシピファイルの読込・書込をHTTP API化する
- ファイル選択UIについて、以下いずれかの方式を採用する（要検討・決定事項）
  - サーバー側の固定ディレクトリ配下のファイル一覧をAPIで返し、ブラウザ側でリスト選択させる
  - ブラウザの`<input type="file">`を用いてアップロードする
- 保存についても、サーバー端末上のディレクトリに書き込む方式とする

### 3.5 スクリプトファイル配置・実行のWeb対応

- **配置**: ユーザーがブラウザ上のUIにスクリプトファイルをドラッグ＆ドロップすると、ブラウザがファイル内容を読み込み、`multipart/form-data`等でサーバーにアップロードする。サーバーは受け取ったファイルを、あらかじめ定めたスクリプト格納ディレクトリ（`SCRIPT_DIR`）配下に保存する
- **実行**: サーバーは、`SCRIPT_DIR`配下に実在するファイルのみを実行対象とする。クライアントから送信された任意のコード文字列を直接実行することはしない
- **パストラバーサル対策**: 実行対象パスを解決した後、`SCRIPT_DIR`配下であることを必ず検証する
- **実行結果の通知**: 装置との通信結果・実行ログは、WebSocket等を用いてリアルタイムにブラウザへ反映する
- **実行ロジックの共通化**: 装置とのコマンド通信を含むスクリプト実行ロジック自体はNode.jsコードとしてElectron版・Web版で共通化し、呼び出し方法（IPC vs HTTP+WebSocket）のみを差し替える

### 3.6 アクセス制御（簡易）

- 起動時にランダムなアクセストークンを発行し、URLパラメータ等で付与する方式、または簡易的なBasic認証の導入を検討する（LAN内限定利用のため必須ではないが、望ましい対策として明記する）

## 4. 非機能要求

### 4.1 セキュリティ

- サーバー側でのスクリプト実行は、任意コード実行のリスクを伴うため、実行対象を`SCRIPT_DIR`配下の既存ファイルに限定する制約を必須とする
- Windowsファイアウォールの許可設定（プライベートネットワークでの許可）が必要になる旨を、セットアップ手順またはドキュメントに明記する

### 4.2 保守性・共通化

- ネイティブ機能利用箇所（設定/レシピ/スクリプト実行）は、インターフェース（例: `FileService`, `ScriptExecutionService`）を定義し、Electron実装とWeb実装をComposition Root（DIパターン）で切り替え可能な設計とする
- ECSコア・Vue UIコンポーネント資産の共通化率を最大化し、Web版追加によるElectron版へのデグレードを防ぐ

### 4.3 ビルド・配布

- ビルドスクリプトをElectronパッケージ用とWebサーバ用の2系統で用意する
- Web版は将来的に`pkg`/`@yao-pkg/pkg`等での単一実行ファイル化を想定する（詳細は別途検討）

## 5. アーキテクチャ方針（概要）

| 処理 | Electron版 | Web版 |
|---|---|---|
| UI表示 | BrowserWindow | ブラウザ（LAN内の任意端末含む） |
| 設定/レシピ読込書込 | IPC（`ipcRenderer.invoke`）→ メインプロセスで`fs` | HTTP API → サーバーで`fs` |
| スクリプト配置 | レンダラーでファイルパス取得 → IPC → メインプロセスで配置 | ブラウザでFile取得 → HTTPアップロード → サーバーで配置 |
| スクリプト実行 | メインプロセスで`child_process`/`vm`実行 | サーバーで`child_process`/`vm`実行（ロジック共通） |
| 実行結果通知 | IPC（`ipcRenderer.on`） | WebSocket |

```ts
// 共通インターフェース例
interface FileService {
  readSettings(): Promise<Settings>;
  writeSettings(data: Settings): Promise<void>;
  readRecipe(id: string): Promise<Recipe>;
  writeRecipe(id: string, data: Recipe): Promise<void>;
}

interface ScriptExecutionService {
  deploy(file: File): Promise<void>;
  execute(scriptId: string): Promise<void>;
  onResult(callback: (result: ScriptResult) => void): void;
}
```

## 6. 未決事項・要検討項目

- レシピファイルの選択UIをディレクトリ一覧方式にするか、アップロード方式にするか
- アクセス制御（トークン方式かBasic認証か、または本版では実装しないか）
- Web版の配布形態（単一exe化するか、Node.js実行環境を前提とするか）
- 複数端末から同時にアクセスされた場合の挙動（想定外操作の扱い。排他制御はスコープ外だが、UI上の注意喚起は要検討）

---

## 7. 移行時の調査事項

- 既存のIPC呼び出し箇所（`ipcMain.handle`/`ipcRenderer.invoke`）の一覧化（設定/レシピ/スクリプト実行の3系統それぞれの呼び出し数・箇所）
- ネイティブ機能利用箇所のうち、上記3つ以外に見落としがないかの棚卸し
